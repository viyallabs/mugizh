## 3. D-04 in detail: identity without Kratos (proposed ADR-32)

**Finding.** Ory Kratos keeps each identity's traits and login identifiers (the phone number for SMS codes, emails) as plain JSON and text in its own database tables. Only some credentials (for example TOTP secrets) are encrypted. That breaks **K-DP-03** ("contact details MUST use field-level encryption with KMS envelope keys; per-patient keys allow crypto-shredding") and the erasure design (the patient key could not shred a phone number held by Kratos). Workarounds (storing an HMAC as the Kratos identifier and resolving it in our SMS courier) remove most of what Kratos offers and add a fragile path. Keycloak, the documented fallback, has the same limit.

**What is built instead** (identity module, all secrets hashed or field-encrypted):
- Patient sign-in by **SMS OTP** (6 digits, 5 minutes, at most 5 attempts, then lock with backoff; limits per number, device and IP; `+91`-style allow-list from the country pack; daily spend cap with a kill switch) (TM-01, TM-02, E-SEC-01).
- **Device binding** with a device public key; refresh needs a signature from that key (K-SEC-03).
- **New device on an existing account** gets a restricted session that cannot read health data until re-verification passes (E-DP-22, TC-16).
- Professionals: **TOTP MFA** (RFC 6238, `pquerna/otp`), secret field-encrypted; passkeys later via `go-webauthn` (needs an ADR line in dependencies.md). Step-up tokens for signing (P08).
- Phone stored encrypted with the patient key plus a blind index (encryption-design §5).

**Founder action:** approve ADR-32 or ask for the Kratos workaround. Until then the code is built this way because it is the only option that meets the contract.
